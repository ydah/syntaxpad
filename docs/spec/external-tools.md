# External parser-generator integration

`@syntaxpad/tools` runs Bison or Lrama and normalizes generator-specific output. It is independent
of VS Code; `syntaxpad-vscode` owns configuration, Workspace Trust, consent, diagnostics, and view
publication. The complete command and configuration declarations are maintained in the
[extension manifest](../../packages/syntaxpad-vscode/package.json).

## Adapter boundary

The public boundary accepts a `ConflictRunRequest`: tool kind, executable, additional argument
array, decoded grammar source, cancellation signal, timeout, and capture limit. It exposes two
operations:

- `describeConflictInvocations` produces every possible executable/argument-array invocation for
  consent UI without running a process.
- `runConflictAnalysis` creates the temporary workspace, executes the required adapter attempts, and
  returns one normalized `ConflictReport`.

The runner never receives VS Code documents or protocol objects. Report parsers consume captured
`ToolExecution` metadata plus structured or text report content.

## Generator strategies

### Bison

The primary attempt requests XML with state, lookahead, solved-conflict, and counterexample data and
also requests counterexample warnings. If XML cannot be parsed, a second invocation requests a
compatible XML report without counterexamples. If that also fails, a third invocation requests the
verbose text report. A parsed primary XML report may be supplemented with counterexamples from the
text report generated by the same run.

The XML parser maps states, rules, lookaheads, resolutions, and conflict entries into the normalized
model. The text parser recognizes state summaries and diagnostic conflict totals. Fallback selection
is reported in `messages` rather than hidden.

### Lrama

The runner requests a states, lookaheads, and counterexamples report file and parses its state
headings conservatively. Lrama has no stable structured report schema at this boundary. When exact
state details cannot be recovered but diagnostics contain totals, the adapter returns counts only;
otherwise it returns a failed report.

## Normalized report

Every attempt returns the same shape:

- `detail`: `full`, `counts-only`, or `failed`;
- `format`: `bison-xml`, `bison-text`, `lrama-text`, or `none`;
- `totals`: shift/reduce and reduce/reduce counts;
- `conflicts`: bounded conflict entries with kind, optional state/token/counterexample, and mapped
  rule names;
- `messages`: degradation, execution, and parse information;
- `truncated`: whether captured process or report content exceeded a read limit; and
- `tool`: the selected generator kind.

The VS Code layer maps reported rule names back to ranges in the grammar, publishes conflict
diagnostics, updates the grammar view, and shows a full/counts-only/failed notification.

## Run lifecycle

1. The command resolves an explicit document URI or the active editor and requires a `.y`/`.yy` or
   `yacc` document in a trusted workspace.
2. Settings are resolved for the target document and runtime-validated. The user confirms the
   displayed invocation set for a previously unseen configuration signature.
3. The current decoded document text is copied to a mode-`0600` `input.y` in a new temporary
   directory. The generator receives explicit report and parser-output paths in that directory.
4. The process is spawned with an argument array, `shell: false`, ignored stdin, and captured stdout
   and stderr. Cancellation and timeout both request process termination.
5. Reports are read up to the configured capture limit and normalized. The temporary directory is
   recursively removed in `finally`.
6. The extension maps the result to diagnostics and a version-labelled panel report.

The security boundary and the limits of these controls are canonical in
[the security specification](security.md). Performance contracts and observed results remain in
[quality budgets](../quality/budgets.md) and [quality records](../quality/records.md).

## Current limitations

- Timeout and cancellation call `child.kill()` once and wait for process close. This is a soft
  termination request: there is no escalation and no process-group or descendant-tree hard kill.
- The run captures source text before awaiting the generator, but completion uses the mutable
  `TextDocument`'s then-current text and version for mapping/publication. If the document is edited
  during a run, a report for the old source can be published under the new version.
- There is no per-document run generation or cancellation guard. Parallel runs can complete out of
  order, allowing an older result to replace a newer result and its diagnostics.
- Parseable XML or recognizable state summaries can produce `detail: full` even when the generator
  exits nonzero; report recognition is not equivalent to successful grammar generation.
- When the generator rejects the grammar and no usable report exists, the first user-facing message
  is the generic report-interpretation failure; the generator diagnostic follows it. This can hide
  the actual grammar rejection in the initial notification.
- Lrama compatibility is based on tolerant text parsing, not a versioned structured schema. Report
  layout, accepted report flags, and accepted grammar syntax vary by tool version; unsupported
  syntax can therefore appear as either a degraded report or a generator failure.
